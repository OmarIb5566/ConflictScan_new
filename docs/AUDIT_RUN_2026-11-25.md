## 3. Timeline and efficiency

| Stage | Wall time | Model time | Calls |
|---|---|---|---|
| Read documents (qwen3:14b) | ~6 min | 548 s | 22 (11 cached) |
| Read drawings (qwen2.5vl:7b) | **~96 min** | 14,209 s | 865 (108 cached) |
| Compare (qwen3.6:27b) | **~68 min** | 3,518 s, **3.27 M prompt tokens** | 645 |
| Verify (gpt-oss) | (inside Compare) | 501 s | 61 |
| Draft RFIs (qwen3.6:27b) | ~9 min | 638 s | 35 |
| **Total (after restart)** | **2 h 54 min** | | |

**Incident.** At 15:17 a code fix was saved while the app was running as `python api.py`. That is the Flask *development* server with the auto-reloader on, and `CONFLICTSCAN_DEBUG` defaults to `1`. The reloader killed the worker. The job queue recovered the scan and restarted it from the beginning, losing 43 minutes. The response cache replayed the finished work in seconds. This was the auditor's fault, but it also exposes a real production risk (finding E1).

**Efficiency findings**

- **E1. The development server is the default.** `python api.py` starts with the debug reloader on, so any file change restarts every running scan. **Fix:** production uses `serve.py` (waitress) only, and `api.py` defaults to debug off.
- **E2. Runaway vision replies.** Before the fix, **24% of tiles** hit the 8,192-token cap. The 7B vision model had looped, repeating one item up to 60 times. Those tiles took half the vision time and were then **discarded entirely**: the JSON failed to parse and the tile was silently treated as empty. **Fixed during the audit:** replies are now streamed and stopped when they repeat verbatim, complete items are recovered, duplicates are removed, cut-off replies are not cached, and cut-off or failed tiles are reported. Measured live: tile time fell from **38 s to 17 s** on average. Of 678 tiles, 120 were cut off; their items were kept, with no data loss beyond what the model had produced.
- **E3. Pair explosion.** **7,452 pairs** were sent to the 27B adjudicator, and **7,361 of them came from "baseline links"**. That is the vision model tagging drawing items with spec-checklist IDs, 2.7 tags per item on average. One spec clause (B-018, pump-station columns) was tagged onto **657 drawing items**, tank slabs included. With proper gating, the comparison would be a few hundred pairs and about 5–10 minutes.
- **E4. Drawings have a text layer, but the vision model reads everything.** These PDFs are vector drawings with text layers. Rebar callouts, levels and titles could be extracted without a model, leaving vision for geometry and context. That would cut most of the 96 minutes.
- **E5. Duplicate input not detected.** The same specification was uploaded as .docx and .pdf. Nothing flagged it, and the two copies produced different extractions (see A6).

## 4. Accuracy

### 4.1 Composition of the 346 findings

| Bucket | Findings | Auditor's judgement |
|---|---|---|
| **Pump-station spec clause compared with a *tank or site* drawing** | **202** | False: different structures. Example: tank wall bars `T16@200` treated as conflicting with "pump-station columns: four Y12". |
| Disputed by the verifier (correctly excluded) | 83 | Mostly false, correctly set aside |
| Arbitrary number taken as the value (`2500`, `10000`, `5T16` against areas, depths or door sizes) | ~25 | False |
| Drawing against drawing (internal / interface) | 9 | False, or duplicates (D-001 to D-004 are one finding ×4, comparing **different tanks'** "Grid A") |
| Low-confidence, unverified value | 14 | Mostly false |
| **Plausibly real** | **~9 (3 issues)** | See 4.2 |

**Counted as real by the scan: 263. Plausibly real: about 9. Precision ≈ 3–4%.** Of the 11 "critical" findings, **none** holds up: guardhouse "10,000 vs 30 m²", pit latrine "2.5 m vs 15 m", soakpit "250 vs 10 m" and so on are dimension strings set against requirements of a different kind.

### 4.2 Issues that look real (the engineer should confirm)

1. **Fence posts:** the drawings show *precast concrete fencing posts*; the spec requires *galvanised SHS 50×50×2 mm steel posts at ≤3 m centres*. Raised 6 times (D-057, 058, 062, 175, 312 and 013).
2. **Pump-station external walls:** the PS-GAH-2 architecture sheet shows *200 mm thick*; the spec requires *250 mm fired-clay brick masonry* (D-119, D-157).
3. **Valve-chamber access door:** a drawing detail shows *1000×1000*; the spec requires a *1000×2120 mm* clear opening (D-324, low confidence; check that the drawing value is the door and not a cover).

These are the kind of findings the tool exists to produce. They are buried under about 250 false ones, and three of the 40 drafted RFIs contain them.

### 4.3 Root causes, in order of impact

- **A1. No scope gate between a spec clause and a drawing.** The clause's own heading says *"Chapter XII Pumping Station PS-GAH-2 — 12.2.3 Frame and Walls"*, and the drawing file says *Tanks_-_Structural_MR-MWU01*. Nothing compares the facility or structure the clause applies to with the one the drawing shows. This alone accounts for **58%** of all findings.
- **A2. Baseline tags are trusted as pairs.** `_baseline_linked_pairs` turns every ID the vision model attached into a comparison, after only a location-compatibility check. The model tags liberally; for example, a fence-post item was tagged B-011 on every line.
- **A3. No check that two values are the same kind of quantity.** A bare `2500` is compared with "minimum thirty square metres" and "fifteen metres depth". A deterministic check (length / area / count / rebar callout / grade / text) should reject the pair before any model sees it.
- **A4. Ungrounded values drive major findings.** **48%** of the vision model's values do not appear in the sheet's own text layer. They are marked `verify` and kept out of *critical* findings, but they still produce *major* ones, and 53 major findings rest on them.
- **A5. The verifier rubber-stamps.** gpt-oss **confirmed 255** findings, including "guardhouse 10,000 vs 30 m²" and tank rebar against pump-station columns. Its prompt does not make it check *same structure, same element, same quantity type*. Where it did dispute findings, its reasons were good ("drawing refers to bars, spec refers to posts"), so it can do the job when asked the right question.
- **A6. Extraction is inconsistent.** The identical spec gave **39 requirements as .docx and 91 as .pdf**.
- **A7. Duplicates are not merged.** One spec clause produced **181 findings**. D-001 to D-004 are word-for-word identical. Findings should be grouped by (spec clause, element, attribute).
- **A8. The RFIs inherit all of it.** 263 findings produced 40 RFIs of about 8 findings each, grouped by size rather than by issue. Subjects like *"Discrepancy between structural drawings and specs for reinforcement details"* would be rejected by a consultant.
- **A9. The headline contradicts itself.** "201 significant conflicts … The documents agree on the large majority of what was compared." Both statements are technically true, but when 7,452 pairs are mostly unrelated, "agreement" is meaningless.

### 4.4 Reading-quality observations

- Sheet 10's revision was read as "200", a dimension misread as a revision.
- On sheet 7, the "framing system" field holds rebar callouts (`T12@100, T12@150…`).
- 2 of 91 sheet overviews were cut off and lost entirely, including sheet number, title and revision (1,600 repeated `"200"` entries). A fix is ready (section 6, F0).
- 60 drawing values were unreadable and correctly excluded, and listed for the engineer.
- The checklist given to the drawing reader was capped at **60 of 106** baseline items. Twenty spec items (crane capacity, plinth wall, gate size, guardhouse area…) were "not located on the drawings".

## 5. What worked (keep this)

- **Robust pipeline.** 13 files, 86 sheets and 2,000+ model calls with no crash. Three empty verifier replies were retried successfully. All models ran locally; nothing went to the cloud.
- **Recovery.** A killed worker was detected, the job was requeued and finished. Cached work replayed instantly.
- **Traceability is excellent.** Every finding carries verbatim quotes, file, sheet, grid and detail for both sides. That is why this audit took minutes instead of days, and why an engineer can reject a false finding in seconds.
- **The honesty features did their job where they apply:**
  - The large size gap between the sets was detected, so no fake "scope gap" findings were raised against the specification.
  - Limitations are reported in plain language: cut-off tiles, unverified values, checklist cap, unread baseline items.
  - The verifier's 83 disputed findings are shown, are not counted, and are kept out of the RFIs.
  - Low-confidence values are kept out of *critical* findings.
- **The loop-stop fix** halved drawing-reading time with no loss of distinct items. It was checked against all 129 cached real replies.
- **The real issues were found.** Recall on what matters is not the problem here; precision is.

## 6. Fix plan (priority order)

| # | Fix | Effect | Effort |
|---|---|---|---|
| **F0** | *(ready)* General cut-off JSON recovery (sheet overviews too); `api.py` debug off by default | No lost sheets; no restart risk | 15 min |
| **F1** | **Scope gate.** Tag each spec clause with the structure or facility its chapter or heading names, and each drawing with the structure its file or sheet title names. Pair only when they match, or when either side is generic. | Removes about 200 false findings (58%) | 2–3 h |
| **F2** | **Baseline tags must earn the pair.** Accept a tag only if the drawing item's element and attribute match the baseline item's element and attribute (tokens or embedding). At most 2 tags per item. | Pairs fall from 7,452 to a few hundred; comparison from 68 to about 10 min | 1–2 h |
| **F3** | **Same-quantity check** before the adjudicator: classify both values (length, area, depth, count, rebar, grade, material, text) and drop mismatched pairs | Removes the "2500 vs 30 m²" class | 2 h |
| **F4** | Ungrounded (`verify`) values may raise **minor** findings at most, or "please confirm" items, never major or critical | Removes about 50 | 30 min |
| **F5** | **Verifier checklist.** Same structure? Same element? Same quantity type? Value actually stated? A "no" on any question means not a conflict. Pass it the file and sheet titles. | Second line of defence | 1 h |
| **F6** | Group findings by (spec clause, element, attribute) → one finding listing every drawing location; one RFI per issue | 181 findings become about 5; RFIs become readable | 2 h |
| **F7** | Detect near-identical files within a set (text similarity) → warn and use one copy | Consistent extraction | 1 h |
| F8 | Text-layer-first drawing reading (vector PDFs); vision only for context and geometry | Drawing stage roughly 96 → 30 min | 1 day |
| F9 | Give the drawing reader the whole checklist (or batches of it), not the first 60 | Recall on the 46 items now left out | 1 h |
| F10 | Stage checkpoints, so a restarted scan resumes from its last finished stage | Resilience | 3 h |

**Acceptance test after F0–F7:** re-run this exact project; the cache makes it about 1 hour. Pass criteria:
- the 3 real issues are still found;
- no more than about 15 findings in total;
- no pump-station clause is paired with a tank drawing;
- no critical finding rests on a bare number.

Then run the 6-RFI benchmark (`bench/run.py`) to make sure recall has not dropped.

## 7. What is missing (beyond fixes)

- **A labelled evaluation set.** There is no ground truth for any real project. Precision and recall can only be estimated by hand, as here. Before production, at least 3 projects should have engineer-confirmed findings that every change is measured against.
- **Engineer feedback loop.** Accepting or rejecting a finding should feed the RFI memory and a per-project "not a conflict" list, so the same false pair is never raised twice.
- **Scan-size guard and ETA.** An 86-sheet upload on a workstation GPU should warn about the 2–3 h runtime before starting, and offer "pump-station drawings only" focus or the A100 profile.
- **Per-finding "why paired" explanation** (keyword / meaning / baseline tag), shown in the UI, so reviewers can spot systematic mis-pairing at a glance.

**Real issues found across the runs:**
- fence posts: precast concrete vs galvanised SHS steel;
- pump-station external walls: 200 mm vs 250 mm;
- pump-station walls: block vs fired-clay brick;
- intermediate beam: 200×400 vs 200×450;
- septic blockwork: 230 mm vs the 100/150/200 mm block sizes;
- columns: 200×400 vs 200×200 (plausible).

**Still open**

1. **Run-to-run recall.** Each run finds 3–5 of the 6 real issues. Model output
   varies between runs at temperature 0.1, and the drawing reader does not label
   every element the same way each time. Next steps:
   - temperature 0 with a fixed seed for the reading and comparison models, so a
     re-run reproduces its result;
   - labelled evaluation projects to measure recall.
2. **Severity "critical".** In every run, the critical findings were false. They
   are now caught by the bare-number and magnitude rules. Watch the first
   production scans for any critical finding and confirm it by hand.
3. **Ollama parallelism must be set on every model server.** Without
   `OLLAMA_NUM_PARALLEL`, reading takes about 2× longer (INSTALL.md §6).
